# Пилот: состояние и запуск

Пилот до 20 сотрудников, отдельный адрес `/pilot/`. Корень сайта пока оставлен демонстрацией.

Реализовано: PostgreSQL, вход с проверкой Telegram initData и срока действия, серверные сессии, одноразовые приглашения на 7 дней, регистрация через /start, добровольная привязка собственного контакта через /phone, роли, редактор текстового материала и теста, проверка перед публикацией, неизменяемые опубликованные версии, назначения с дедлайном и лимитом попыток, ознакомление, серверная оценка и история попыток, результаты руководителя, уведомления в личном чате бота через очередь с повторами.

Пока нет: ИИ-генерации, загрузки бинарных документов, аудио, редактируемых глав, QR, событий в пилотном кабинете, автоматических напоминаний о дедлайнах и внешней копии бэкапов. Просроченные задания можно сдать: дедлайн информационный. Рабочие курсы и тесты ещё должны быть подготовлены и утверждены по материалам MOJO; демонстрационные вопросы автоматически не импортируются.

## Развёртывание
`bash /opt/service/pilot/deploy-pilot.sh`

Создаёт отдельные контейнеры PostgreSQL/API и сеть Docker без открытого наружу порта базы. Caddy проксирует `/api/*` и `/pilot/*`. Старое демо и premium-ai-manager сохраняются.

Секреты: `/etc/service-academy.env`, права 600. Они не попадают в репозиторий. Не копировать сюда env и дампы.

Владелец запускает в своей SSH/Selectel-консоли:
`sudo python3 /opt/service/pilot/configure.py`

Скрипт скрыто запрашивает токен, проверяет имя бота, запрашивает Telegram ID владельца и перезапускает только пилот. Затем владелец отправляет /start боту. Никто другой не получает управленческих прав автоматически. Менеджеров точек добавляет администратор явно, после проверки Telegram ID.

Если у бота есть чужой webhook, worker останавливается без его удаления; нужно сначала согласовать миграцию. Уведомления отправляются после назначения. Первое подключение каждого сотрудника — через приглашение и нажатие «Старт» в личном чате. При сетевой неопределённости Telegram не гарантирует exactly-once: возможен повтор уведомления; результаты теста идемпотентны.

## Проверки
`python pilot/test_pilot.py` проверяет подпись и оценку. С DATABASE_URL дополнительно создаётся временная схема `pilot_test_*`, в ней проверяются реальные PostgreSQL/API/права/попытки/приглашения и очередь с замоканной отправкой. Схема удаляется после проверки. Deploy обязан пройти эти проверки до замены API.

## Бэкапы
Каждый день 03:17 по времени сервера: pg_dump в `/var/backups/service-academy`. Проверяется читаемость архива. Это локальная копия: до массового запуска настроить отдельное хранилище и проверить полное восстановление. Автоудаления резервных копий нет; контролировать диск.

## До допуска реальных участников
1. Настроить токен и ID владельца, проверить вход именно владельцем.
2. Создать и утвердить реальный урок/тест.
3. Подключить второго тестового участника через одноразовую ссылку.
4. Назначить ему материал; проверить реальную доставку сообщения, прохождение и результат руководителя после перезапуска.
5. Утвердить правила работы с данными сотрудников и ответственного, настроить внешнюю копию базы.
6. Только после проверки приглашать остальных.


## Открытые кейсы и Yandex AI Studio — ветка пилота

Реализована отдельная вкладка «Практика»: руководитель создаёт кейс с **компетенцией, наблюдаемым действием, ситуацией, критериями и версией источника**, просматривает и публикует его. Сотрудник отвечает свободным текстом и получает от модели индивидуальную **учебную** обратную связь; текст ответа и результат хранятся в PostgreSQL. Это не аттестация и не автоматический допуск.

API совместим с официальным Yandex AI Studio Completions. В **закрытый** файл `/etc/service-academy.env` (права 600) добавляют:
- `YANDEX_API_KEY` — ключ с разрешением `yc.ai.foundationModels.execute`;
- `YANDEX_FOLDER_ID` — идентификатор каталога с доступом к модели;
- `YANDEX_MODEL=yandexgpt-5.1` — необязательный параметр (точное имя проверьте в каталоге моделей перед вводом).

Не добавлять ключ в GitHub, ChatGPT, скриншоты или публичные URL. Файлы с настоящими ServiceBook, меню и подготовленными уроками также не публикуются в GitHub.

Пока ключ не настроен, `POST /api/cases/{id}/practice` возвращает 503 без ложного «оценивания». Если провайдер недоступен, ответ не засчитывается и выводится ошибка.

В ИИ-запрос отправляются только текст учебного кейса, утверждённые критерии и свободный ответ — без Telegram ID, имени и номера телефона. Передача данных сотрудника стороннему процессору требует согласованного работодателем порядка обработки. Не разрешайте вводить сведения о реальных гостях. Проверка типовых контактных данных — дополнительный фильтр, не гарантия отсутствия ПДн. До пилота уточнить хранение запросов у Yandex AI Studio и порядок получения согласий.

Затраты ограничены пятью сохранёнными разборами на пользователя за 24 часа; требуется также установить квоту бюджета на стороне Yandex. Следующие шаги безопасности: межпроцессное резервирование вызовов для защиты от параллельного исчерпания лимита и настройка сроков хранения/удаления ответов.

Для **приватного** импорта сценариев (до 20 за раз) используй:
`docker exec -i service-academy-api python import_case_drafts.py < /secure/private_cases.json`
Для **приватного** импорта курсов используйте существующий:
`docker exec -i service-academy-api python import_drafts.py < /secure/private_courses.json`

Перед импортом владелец должен авторизоваться в боте через /start. Все импортированные материалы остаются **черновиками**. Их проверяет и публикует уполномоченный менеджер по сервису. Реальные исходные файлы не хранятся в GitHub.

Тесты:
`python -m unittest test_cases test_pilot` (в каталоге pilot с установленными requirements); интеграционный контур с PostgreSQL запускается при наличии DATABASE_URL.
**Не заявлять о рабочем Yandex API, пока не проведена реальная отправка учебного ответа и проверка сохранения после перезапуска.**


## Карточки вина (два направления)

В черновике курса менеджер открывает **Программы → Дополнительные действия → Карточки вина**.
Каждая позиция заполняется **только по проверенной винной карте**: точное название,
сорт (или ассамбляж), страна, регион, документ-источник/версия. Пустые поля и
дубли названий отклоняются. ИИ ничего не выводит из названий вина автоматически.

При публикации курс получает неизменяемый набор карточек. Сотрудник повторяет:
1. название → сорт, страна и регион;
2. сорт, страна, регион → название.

Если несколько вин имеют одинаковое сочетание сорта, страны и региона, обратная
карточка содержит **все** соответствующие названия, а не ложный единственный ответ.
Карточку надо перевернуть перед самооценкой «Знаю / Трудно / Повторить». Отметки
сохраняются отдельно в PostgreSQL для каждого сотрудника; трудные карточки
возвращаются в текущую очередь повторения. Это **самопроверка памяти**, а не
изменение проходного балла, экзамена, допуска или прошлых результатов.

Набор редактируется только **до** публикации. Для изменений действующей винной
карты создаётся новая версия курса; существующие попытки не стираются. При
стандартном копировании курса винные карточки намеренно **не дублируются
автоматически**: менеджер должен сверить их с новым источником и подтвердить.
В существующие курсы без набора вина не добавляется обязательный этап.

API: `GET /api/wine-cards/{cid}`, `PUT /api/wine-cards/{cid}` (менеджер, только
черновик), `POST /api/wine-cards/{cid}/rating` (только опубликованный курс).
Прогресс хранится в `wine_card_progress`, набор в `course_wine_cards`.
При обновлении `schema.sql` применяется идемпотентная миграция.

Проверки: `python -m unittest test_wine_cards` с `DATABASE_URL` запускает
отдельную PostgreSQL-схему, проверяет права, публикацию, сохранение и
неизменность оценок экзамена. Перед выкладкой на Selectel также проверить на
реальном iPhone работу переворота, длинные названия и повторный вход в Telegram.
