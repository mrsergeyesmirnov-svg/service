# Пилот: состояние и запуск

Пилот до 20 сотрудников, отдельный адрес `/pilot/`. Корень сайта пока оставлен демонстрацией.

Реализовано: PostgreSQL, вход с проверкой Telegram initData и срока действия, серверные сессии, одноразовые приглашения на 7 дней, регистрация через /start, добровольная привязка собственного контакта через /phone, роли, редактор текстового материала и теста, проверка перед публикацией, неизменяемые опубликованные версии, назначения с дедлайном и лимитом попыток, ознакомление, серверная оценка и история попыток, результаты руководителя, уведомления в личном чате бота через очередь с повторами.

Пока нет: ИИ-генерации, загрузки бинарных документов, аудио, редактируемых глав, QR, событий в пилотном кабинете, автоматических напоминаний о дедлайнах и внешней копии бэкапов. Просроченные задания можно сдать: дедлайн информационный. Рабочие курсы и тесты ещё должны быть подготовлены и утверждены по материалам MOJO; демонстрационные вопросы автоматически не импортируются.

## Развёртывание
`bash /opt/service/pilot/deploy-pilot.sh`

Создаёт отдельные контейнеры PostgreSQL/API и сеть Docker без открытого наружу порта базы. Caddy проксирует `/api/*` и `/pilot/*`. Старое демо и premium-ai-manager сохраняются.

Секреты: `/etc/service-academy.env`, права 600. Они не попадают в репозиторий. Не копировать сюда env и дампы.

Владелец запускает в своей SSH/Selectel-консоли:
`sudo python3 /opt/service/pilot/configure.py`

Скрипт скрыто запрашивает токен, проверяет имя бота, запрашивает Telegram ID владельца и перезапускает только пилот. Затем владелец отправляет /start боту. Никто другой не получает управленческих прав автоматически. Менеджеров точек добавляет администратор явно, после проверки Telegram ID.

Если у бота есть чужой webhook, worker останавливается без его удаления; нужно сначала согласовать миграцию. Уведомления отправляются после назначения. Первое подключение каждого сотрудника — через приглашение и нажатие «Старт» в личном чате. При сетевой неопределённости Telegram не гарантирует exactly-once: возможен повтор уведомления; результаты теста идемпотентны.

## Проверки
`python pilot/test_pilot.py` проверяет подпись и оценку. С DATABASE_URL дополнительно создаётся временная схема `pilot_test_*`, в ней проверяются реальные PostgreSQL/API/права/попытки/приглашения и очередь с замоканной отправкой. Схема удаляется после проверки. Deploy обязан пройти эти проверки до замены API.

## Бэкапы
Каждый день 03:17 по времени сервера: pg_dump в `/var/backups/service-academy`. Проверяется читаемость архива. Это локальная копия: до массового запуска настроить отдельное хранилище и проверить полное восстановление. Автоудаления резервных копий нет; контролировать диск.

## До допуска реальных участников
1. Настроить токен и ID владельца, проверить вход именно владельцем.
2. Создать и утвердить реальный урок/тест.
3. Подключить второго тестового участника через одноразовую ссылку.
4. Назначить ему материал; проверить реальную доставку сообщения, прохождение и результат руководителя после перезапуска.
5. Утвердить правила работы с данными сотрудников и ответственного, настроить внешнюю копию базы.
6. Только после проверки приглашать остальных.

## Импорт подготовленной программы
Менеджер по сервису открывает «Обучение», выбирает **JSON-пакет** курсов и нажимает «Импортировать черновики». API проверяет все курсы до вставки, создаёт их одной транзакцией и не публикует. Повторная загрузка идентичного пакета блокируется. Редактирование и утверждение каждого курса остаются за менеджером.

Это промежуточный импорт готового учебного контента, не PDF/DOCX-загрузка и не генерация через LLM. В публичный репозиторий нельзя загружать внутренние материалы ресторана и ключи к модели. Для DOCX/PDF→текст→черновик теста потребуется отдельный приватный обработчик файлов, разрешённый API-провайдер, проверка источников и редакторское утверждение.
